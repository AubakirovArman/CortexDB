# RPO/RTO Boundaries

Status: Core Alpha / Production Candidate local boundary.

This document defines what CortexDB can currently claim for a single-node
deployment. It does not define a managed-service SLA.

## Definitions

- **RPO**: maximum accepted durable data loss after a failure.
- **RTO**: target time to recover service after a failure.

## Current Single-Node RPO

CortexDB writes operations through the WAL before updating the MemTable. In
`Strict` durability mode, the writer syncs durable records before acknowledging
the operation. In `Balanced` mode, group commit can acknowledge within a larger
durability window.

Practical Core Alpha boundary:

| Mode | RPO claim |
| --- | --- |
| `Strict` | Intended near-zero acknowledged-write loss on local filesystem failures that honor `fsync`. |
| `Balanced` | May lose the most recent unsynced group on process/host failure. |
| Backup restore | RPO is the age of the latest validated backup or offsite staged copy. |

Release evidence:

```bash
make backup-drill-check
make backup-offsite-check
make backup-rpo-rto-profile-check
make backup-restore-production-pack-check
make crash-fault-check
```

## Current Single-Node RTO

RTO depends on database size, WAL tail length, storage device, and whether the
operator restores from local backup or offsite staging.

Current local evidence is generated by:

```bash
make single-node-performance-check
make performance-trend-check
make backup-drill-check
make backup-rpo-rto-profile-check
make backup-restore-production-pack-check
make production-candidate-check
```

`target/single-node-performance/report.json` records the current local
single-node lifecycle duration. `target/performance-trends/report.json` compares
the current local p95/p99 load and embedded-engine flow evidence with release
history. `target/backup-drill/report.json` records local backup, restore,
validate, and readback evidence. `target/backup-rpo-rto/report.json` records
small, medium, and large local backup/restore profiles with measured backup,
restore dry-run, and restore durations. `target/backup-restore-production-pack/report.json`
aggregates local drill, offsite staging, RPO/RTO profile evidence,
encrypted-backup gate coverage, and the current RPO/RTO boundary in one release
artifact.

## Local Backup/Restore Profiles

The repeatable profile gate is:

```bash
make backup-rpo-rto-profile-check
```

It writes:

```text
target/backup-rpo-rto/report.json
```

Current profile definitions:

| Profile | Cells before backup | Payload size |
| --- | ---: | ---: |
| small | 11 including WAL-tail probe | 128 bytes |
| medium | 101 including WAL-tail probe | 512 bytes |
| large | 501 including WAL-tail probe | 1024 bytes |

For each profile, the gate measures:

- backup duration;
- restore dry-run duration;
- restore duration;
- bytes copied/checked;
- restored validation output;
- readback of checkpointed and WAL-tail cells;
- exclusion of a post-backup write from the restored copy.

The post-backup write check is the data-loss boundary proof for backup restore:
the restored copy includes writes durable before the backup starts and does not
claim writes that happen after that backup point.

## Operator Recovery Sequence

1. Stop the server.
2. Preserve the failed database directory for inspection.
3. Run `cortexdb validate ./db` if the directory is readable.
4. If validation fails, restore the latest validated backup:

   ```bash
   cortexdb restore ./backups/cortexdb-latest ./db.restored
   cortexdb validate ./db.restored
   ```

5. Start the server on the restored directory.
6. Run smoke checks:

   ```bash
   make smoke-test
   make openapi-contract-check
   ```

## Non-Goals

- No cross-region RPO/RTO claim.
- No managed service uptime claim.
- No production distributed failover claim.
- No KMS-backed encrypted backup or compliance custody claim; see
  [`ENCRYPTED_BACKUPS_DESIGN.md`](ENCRYPTED_BACKUPS_DESIGN.md).
